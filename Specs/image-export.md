# Image Export Feature

The Image Export feature card lets the user pick one maze **rendering mode** for image export, then configure that mode's own settings. Actual image export (saving/downloading) is out of scope for this ticket — infrastructure only.

## Feature Card Status

| Condition | Status | Comment |
|-----------|--------|---------|
| No maze generated (`nodes.length === 0`) | `unavailable` | "Generate maze first" |
| Maze exists, no render mode selected | `warning` | "Render mode not selected" |
| Maze exists, a render mode is active | `set` | "Active: {mode label}" |

Computed by `computeImageExportCard` (`FeaturesPanel.tsx`), covered by `featuresPanel.test.ts`.

## Switcher: one active mode, no default

`activeRenderMode: RenderModeId | null` (`imageExportSlice.ts`) starts as `null` — the switcher has **no default selection**. The user must explicitly pick a mode; until then the card shows the `warning` status above.

Clicking a switcher item (`ImageExportFeature.tsx`):
- **Inactive item** → becomes the active mode (`setActiveRenderMode`) and its own settings `SidePanel` opens (`setOpenRenderModeSettings(mode)`) — one click both switches and shows that mode's settings, never leaving a panel open for the previously active mode.
- **Active item** → toggles its own settings `SidePanel` open/closed (`setOpenRenderModeSettings`).

`openRenderModeSettings: RenderModeId | null` is independent of `openCard` — closing the whole Image Export card doesn't clear it, but the panel itself only renders while the card is open (rendered on the canvas's `SidePanel` slot, same interaction pattern as post-edit/preset split-node panels).

## Render mode registry

`imageExportRegistry.ts`'s `RENDER_MODES: RenderModeDescriptor[]` is the single source of truth for the switcher's items:

```typescript
interface RenderModeDescriptor {
  id: RenderModeId;
  label: () => string;
  SettingsPanel: React.ComponentType | null; // null = no settings yet
}
```

Adding a new mode: one `RenderModeId` union member, one `RENDER_MODES` entry, one `ImageExportRenderer.createModeRenderer` case, and (if it has settings) one `SettingsPanel` component. No other list to keep in sync.

`resolveRenderMode(id)` looks up a descriptor by id and **returns `null` for an unknown id — it never throws**. This matters once `activeRenderMode` starts getting persisted to project files (planned, alongside per-mode settings, in a future ticket): a project file naming a since-removed/renamed mode must degrade to "no mode selected," not crash the whole `FeaturesPanel`. Every caller (`FeaturesPanel`'s card comment, `ImageExportFeature`'s open-panel lookup) treats a `null` resolution exactly like `activeRenderMode === null`.

## Rendering modes are one-renderer-per-mode, not one-renderer-per-feature

Per `maze-web/CLAUDE.md`'s feature-renderer ownership rule, `ImageExportRenderer` owns the Image Export feature's canvas layer — but internally it delegates to **one renderer instance per active render mode**, since different modes will draw the maze completely differently (walls-as-vectors vs. a future passages-based mode, etc.). `ImageExportRenderer.createModeRenderer` is the only place that switches on `RenderModeId`; each mode renderer gets its own `Container` and is never shared across modes or with any other feature's renderer, even when the visual output happens to match (e.g. "Vector by walls" vs. `GenerationRenderer`).

### "Vector by walls" (`VectorByWallsRenderer`)

Renders the maze **1:1 identically** to the main generation/post-edit view — same walls, same colors — built from the same low-level primitives `GenerationRenderer` uses (`GridRenderer`, `CellFillRenderer` ×2 for floor/closed-cells, `WallRenderer`, `SplitJunctionRenderer`, `TeleportRenderer`, `WaypointsRenderer` for markers), but as its own instances in its own container tree. Visible only while `openCard === "image_export"`.

Its settings panel (`VectorByWallsSettingsPanel.tsx`) has six collapsible sections, backed by `VectorByWallsSettings` (`imageExportSlice.ts`), all collapsed by default:
- **Background** (issue #289) — background color, grid visibility, grid color. Defaults match the editor's own canvas/grid colors (`canvas.stage.background`/`canvas.grid.line`) so the exported image looks identical to the editor view until changed.
- **Tiles** (issues #290/#291) — floor fill color, wall color, corners & ends (round/miter, wall thickness 1-20). Floor and wall settings are folded into one section because both draw on the maze's cells/tiles, unlike Background which draws on the viewport (background rect, grid lines). Defaults match `canvas.floor.default`/`canvas.wall.default`/`WALL_THICKNESS`/round, so the exported image looks identical to the editor view until changed. Wall settings are applied via `WallStyleOverride` (`pixi/renderers/types.ts`) to `WallRenderer`'s `solid` `WallStyle` segments, `SplitJunctionRenderer`'s `wallFaces` segments, and the closed-cells fill color — never the `faint`/`background` `WallStyle` variants or a split passage's own node-identity color, which stay fixed. The "corners & ends" setting drives Pixi's stroke `join` and `cap` together (`round`+`round` or `miter`+`square`) — a `join` only renders where two segments share one continuous stroked path, so `chainSegmentsAtSharedVertices` (`WallRenderer.ts`) first groups wall segments into polylines wherever exactly two segments meet at a vertex (ordinary corners); vertices with any other segment count (T-junctions, dead-ends) stay as separate path endpoints, where `cap` applies instead. **Vertex-chaining only runs when a `WallStyleOverride` is actually passed** — `WallRenderer.render`/`SplitJunctionRenderer.render` fall back to the original independent per-segment stroke (no chaining, no join) when called without one, so `GenerationRenderer`, `PostEditRenderer`, `PresetConnectionsRenderer` and `MazeOverlayRenderer` (all default callers) keep their exact prior look unchanged.
- **Waypoints** (issue #296, corner style/size/gap width added in #302) — start/finish marker appearance, as two plain-label sub-groups ("Start"/"Finish") inside the one collapsible section rather than two separate `SectionHeader`s (too small to warrant independent collapse each). Row order per sub-group: shape, corner style (sharp/round — own per-marker setting, not shared with the Teleports section's `teleportLineCornerStyle`), size (0-1, fraction of the tile size — same convention as `teleportLineSize`), fill color, border color, border width (0-10, `0` draws no border — no separate show-border toggle), gap width (0-10, `0` draws no gap — no separate show-gap toggle). Backed by `MarkerSettings` (`storeTypes.ts`); defaults are a plain sharp-cornered circle matching `canvas.node.start`/`canvas.node.finish` with no border/gap and a size matching the editor's own fixed `NODE_RADIUS * 1.5` marker radius, so the exported image looks identical to the editor view until changed. `buildMazeMarkers` (`mazeSelectors.ts`) takes the marker style as an optional `MarkerStyle` parameter (defaulting to that same borderless sharp circle at the fixed radius) so every other caller — `GenerationRenderer`, `PostEditRenderer`, `MazeOverlayRenderer` — is unaffected; `VectorByWallsRenderer` is the only caller passing a user-configured style, built by its own `buildMarkerStyle` helper which merges `gapColor: floorColor` into the `MarkerSettings` (`gapColor` is not itself a `MarkerSettings` field — always mirrors the floor color, same convention as the one-way indicator's own gap color). `WaypointsRenderer` (`pixi/renderers/WaypointsRenderer.ts`) draws the shape via the shared `drawMarkerShape` (`pixi/renderers/markerShapes.ts` — see "Shared marker shape set" below, `rounded` param driven by `cornerStyle`), then a floor-colored gap ring (widened by `borderWidth + gapWidth`) underneath when `gapWidth > 0`, matching the connector gap's own draw-wider-underneath convention, then strokes a border on top (`alignment: 0`, pixi's outer alignment) when `borderWidth > 0`. Every border/gap stroke in this codebase now uses `alignment: 0` uniformly (GitHub issue #302 follow-up — previously the waypoint marker's border defaulted to pixi's centered `0.5`, the only one that didn't match) specifically so a marker/indicator's own `radius`-like field always denotes its true fill/inner edge and its gap-ring formula is always `radius + borderWidth + gapWidth` everywhere (teleport edge marker, one-way indicator, waypoint marker alike) rather than needing a per-caller `borderWidth/2` correction.
- **One-ways** (issue #292, placed after Waypoints per the issue's own section order; gap width renamed from border width in #302 follow-up, consistent with the marker/connector gap convention — it's a floor-colored separation gap, not a real border) — the one-way indicator's pattern (triangle/chevron/arrow), its own color (always set — no toggleable custom-color fallback), a gap whose color always mirrors the Tiles section's floor color (only its width is settable, 0-10px, `0` draws no gap), corners & ends (round/miter join, independent of the Tiles section's own wall join/cap) and two independent scale knobs: size (0.05-0.5 of the tile size — geometric scale) and thickness (1-10px — chevron/arrow's own line width, no effect on the filled triangle pattern). Built into an `OneWayStyleOverride` (`pixi/renderers/types.ts`) by `buildOneWayStyle` (`VectorByWallsRenderer.ts`, a pure function extracted for unit-testability alongside `buildWallStyle`/`viewportWorldRect`), applied only to `WallRenderer`'s plain wall one-way indicators — never a split passage's own connector arrow (`SplitJunctionRenderer` always draws that with the node's own identity color via `drawDirectionArrow`, unaffected). Defaults to a brighter standalone color (`0xffaa00`) than the editor's own `canvas.edge.oneWay`, plus a 3px gap and larger-than-editor size/thickness, matching the new shared default described below.
- **Teleports** (issue #293, placed after One-ways; edge gap width added in #302) — teleport display style plus per-group customization, both backed by `TeleportRenderer`'s extended `render` API (`pixi/renderers/TeleportRenderer.ts`; every other caller — `GenerationRenderer`, `PostEditRenderer`, `PresetConnectionsRenderer`, `MazeOverlayRenderer` — omits the new params entirely and gets `TeleportRenderer`'s own `DEFAULT_LINE_STYLE`: diamond, round corners, size 0.16, border/connector/connector-gap/edge-gap width all 3, orthogonal connector, periodic arrows (period 5, size 10) — the same defaults `VectorByWallsSettings`' own initial state uses, kept in sync deliberately so every teleport-drawing feature shares one visual baseline). One shared `teleportCornerStyle` (`"sharp"`/`"round"`) rounds the four regular-polygon `MarkerShape`s (`triangle`/`square`/`diamond`/`pentagon`/`hexagon`, via the shared `drawRoundedPolygon`) only; `circle` has no corners, `star`/`cross` have no regular-polygon equivalent — `star`'s reflex corners stay sharp regardless of `cornerStyle` (see "Shared marker shape set" below for why). Marker size (`teleportLineSize`) is a fraction of the tile size (0-1), same convention as the One-ways section's own `size` knob, not a fixed pixel radius. Edges subsection row order: shape, corner style, size, color, border color, border width, then gap width (0-10px, default 3, `0` draws no gap — `teleportEdgeGapWidth`/`TeleportLineStyle.edgeGapWidth`, GitHub issue #302) — a floor-colored ring drawn outside the marker's own border. Every border/gap stroke in this codebase draws with `alignment: 0` (pixi's outer alignment, grows entirely outward from its own shape) uniformly, so a marker's true outer edge is always `radius + borderWidth`, and every gap-ring formula follows the same `radius + borderWidth + gapWidth` shape regardless of caller (teleport edge marker, waypoint marker, one-way indicator alike). Unlike the marker/one-way/connector gaps (which only ever sit under their own single shape), an edge gap ring can visually overlap the point's own connector — so `TeleportRenderer.renderGroups` draws each group as its own 3-sub-pass block (that group's gap rings, then that group's connectors, then that group's points) rather than a single interleaved pass. A gap only ever needs to stay clear of its *own* group's connector/marker geometry; a later group's whole block (gaps, connectors and points alike) still draws on top of an earlier group's whole block, same "later group wins" rule the pre-#302 single interleaved pass used. `planGroupDrawOrder` still buckets connectors per group; `drawGroupGaps`/`drawGroupPoints` are separate per-group draw calls, both invoked inside the same per-group loop as `drawRoutedConnector`.

  There is no longer a `"line"`/`"grouped"` pattern switch — every teleport pair always merges into connection **groups** wherever an endpoint coordinate coincides across pairs (`buildTeleportGroups`, `pixi/selectors/teleportGroups.ts`, union-find over rounded coordinate keys), and grouping alone (independent of whether group *customization* is toggled on) drives canvas **draw order**: `TeleportRenderer.renderGroups` walks `buildTeleportGroups`' groups in order and, for each visible group, draws that group's own connectors immediately before that group's own points, then moves to the next group — not "every connector, then every marker" as two globally-ordered passes. This interleave is resolved by the pure `planGroupDrawOrder` (bucketing a style's routed connectors by the group their endpoints belong to), unit-tested independently of `Graphics`. Everything — connectors and markers, every mode — is drawn into one shared `Graphics` (`TeleportRenderer.view`); there is no separate line-layer/marker-layer split, since draw order between a group's own connector and marker only means anything within one shared surface. A connector's own color/border can be overridden by either endpoint's group. Each group point's fill state — filled (own `color`), outline (empty, `floorColor` fill) or mixed (disagreeing edges through the same point) — is resolved by `resolvePointFillState`. A `"mixed"` point draws a diagonal-split look (shared `drawMarker` helper in `TeleportRenderer.ts`): the filled half is drawn at a slightly larger radius (`r` grown by half the border width) than the outline, masked by a same-formula-at-the-enlarged-scale diagonal cut, so it reaches fully under the border stroke with no visible gap at the seam.

  `buildTeleportGroups` groups by coordinate regardless of whether `fromNode`/`toNode` are set on an edge — the union-find itself only needs coordinates. `fromNode`/`toNode` (populated by `buildTeleportEdges` for `VectorByWallsRenderer`'s caller only) matter solely for `teleportEdgeKey`'s node-id-based group identity (stable across a merge chain the way a position-based fallback key can't fully guarantee for *persisted* customization); callers without node ids (e.g. `PresetConnectionsRenderer`'s `buildPresetTeleportEdges`) still group and draw correctly via the position-based fallback, just without a guaranteed-stable `TeleportGroup.key` across merges — irrelevant to them since they never persist per-group overrides.

- **Splits** (issue #294, placed after Teleports, hidden entirely when the current maze has no split point — `maxSplitNodeCount(nodes) === 0`) — per-split-node-slot identity colors (`splitNodeColors: number[]`) plus a "Special shapes" toggle (`splitSpecialShapes`, on by default). The panel shows exactly as many color rows as the maze's largest split point actually needs (`maxSplitNodeCount`); an untouched slot displays (and, until edited, renders with) `splitSlotColor`'s own default palette (`canvas.node.splitSlots` for slots 0-2, `buildPalette`'s rotating hue wheel beyond that) — `buildEffectiveSplitNodeColors` (`VectorByWallsRenderer.ts`) is what backfills any slot the user hasn't touched yet with that same default before building the render geometry, so the panel's displayed color and the canvas's drawn color never disagree. `setVectorByWallsSplitNodeColor` grows the `splitNodeColors` array on demand, filling any skipped intermediate slots with their own default rather than leaving them sparse.

  The "Special shapes" toggle recognizes two degree-4 split topologies (`SplitSpecialShapeKind`, `pixi/renderers/types.ts`) and draws each as a dedicated shape instead of the generic per-node segment/connector reading: **"bridge"** (two nodes, each a straight-through opposite-face pair) draws as a classic card-map bridge silhouette — the through corridor draws nothing of its own (an ordinary passage straight across the tile), the cross corridor draws as two 4-point polyline edges (`SplitJunctionRenderer.drawSplitSpecialShape`) that run full width at the cross faces, narrow to 60% width over the first/last 20% of the tile's length, and hold a flat 60%-wide deck across the middle 60%. **"diagonal"** (two nodes, each an adjacent-face pair) draws as a single straight wall segment between the tile's two corners where a face of one node meets a face of the other (`corner0`/`corner1`) — not the corner shared between one node's own two faces, which would put one of that node's faces on the wrong side of the cut. Both shapes draw in the plain wall color/width (`WallStyleOverride`, same as `wallFaces`), never a node's own identity color, and always with `cap: "butt"` regardless of the caller's own wall style — a special shape's free ends already sit exactly on the tile's own face boundary, so a round/square cap would protrude past it. `SplitJunctionRenderer.render` draws `wallFaces` first and special shapes on top, so an ordinary neighboring wall's own protruding join (miter/square at a T-junction or tile corner) gets painted over by the special shape's line instead of poking past it.

  `detectSplitSpecialShapeKind`/the shape geometry itself live in `buildSplitPassagesCore` (`mazeSelectors.ts`) and are computed unconditionally alongside a point's ordinary `SplitPassage` entries (`SplitPassagesResult.specialShapes`) — every split-drawing feature gets them, not just `VectorByWallsRenderer`: `SplitJunctionRenderer.render`'s `specialShapes` toggle (`SplitStyleOverride`) defaults to **on** when the caller passes no override at all, so `GenerationRenderer`, `PostEditRenderer`, `PresetConnectionsRenderer` and `MazeOverlayRenderer` all draw recognized bridge/diagonal points with the dedicated shape automatically; only `VectorByWallsRenderer` exposes it as a user-toggleable setting (`splitSpecialShapes`, defaulting to `true`).

  **Group customization** (`teleportGroupCustomization` toggle) layers per-group overrides on top of the base style: every group shares one style unless overridden via `TeleportGroupOverride` (color/borderColor/shape, each falling back to the shared style when unset), stored in `VectorByWallsSettings.teleportGroupOverrides` keyed by `TeleportGroup.key`. Each group's canvas hit area (only wired while the Teleports section is expanded — `interactive: true`, gated on `vectorByWallsSectionsExpanded.teleports` AND `teleportGroupCustomization`) is its own invisible circle of radius `size + 4px`, bucketed into a `hitRadius`-sized spatial grid so a click only scans its own 3x3 cell neighborhood instead of every point of every group. The Teleports section's group list (one `TeleportGroupRow` per group, in `buildTeleportGroups`' sorted-key order) shows an `AlertTriangle` warning icon on any group whose *resolved* color+shape (after its own override falls back to the shared style) exactly matches another group's, but only when the connector style is `"none"` (with a connector drawn, two groups sharing a look are still visually distinguishable by which links connect to what).

  **Selection is click-driven, not hover-driven** (`selectedTeleportGroupKey` in the store, `setSelectedTeleportGroupKey`) — clicking a group's marker on the canvas, or its row in the settings list, selects it; clicking the already-selected group/row again, or pressing `Escape`, clears the selection. Selecting a group hides every other group entirely (`renderGroups` skips the draw call for a non-visible group's connectors/points — cheaper than the alpha-based dimming an earlier version used, since `Container.alpha` composited overlapping translucent shapes independently and showed them through each other at the seam; a hidden group's points still get an invisible hit-circle so it stays clickable to re-select). Collapsing the Teleports section, or turning group customization off, synchronously clears `selectedTeleportGroupKey` (in the same click handler that triggers the collapse/toggle, not a `useEffect` reacting to it afterward) so a stale selection can't dangle invisibly and reappear already-selected next time the section reopens or customization is turned back on. The row's own mouse-over highlight is native CSS `:hover` (`.teleport-group-row` in `global.css`), a separate concern from the `data-selected` attribute driving the actual selection look (both can be true independently without one overriding the other's specificity).

### Shared marker shape set (`MarkerShape`, `pixi/renderers/markerShapes.ts`)

GitHub issue #293 follow-up unified what used to be two separate shape enums/draw functions — a 5-value `MarkerShape` for start/finish waypoints and a 9-value `TeleportShape` for teleports (including `crescent`, a moon shape that read poorly at marker scale and had a geometry defect — see below) — into one 8-value `MarkerShape`: `circle`/`triangle`/`square`/`diamond`/`pentagon`/`star`/`hexagon`/`cross`. Both `WaypointsRenderer` and `TeleportRenderer` draw through the same `drawMarkerShape(g, shape, cx, cy, r, rounded?)`, so waypoints and teleports never diverge in how a given shape looks; `markerPolygonPoints` (regular-polygon corner points, `star` alternating outer/inner radius, `cross` its own fixed 12-vertex layout) backs both the sharp path (`g.poly`) and the rounded path, via `markerShapes.ts`'s own `drawRoundedPolygon` (a general canvas-style per-corner `arcTo` rounder, not `Graphics.roundPoly` — needed since `star`/`cross` have no regular-polygon equivalent `roundPoly` could round). Each corner's radius is capped to half its shorter adjacent edge, and `star`'s reflex (inward-pointing) corners are gated out of rounding entirely (a rounded arc there reads as a spike at typical marker sizes, no radius clamp fixes it). The closed path's `moveTo` start is placed at corner 0's own tangent-out point (`cornerTangentPoint`, `radius / tan(halfAngle)` from the vertex along the edge — not a naive edge-midpoint, which only happens to be correct when both corners sharing that edge round equally) so the path's start exactly matches where the loop's final `arcTo` call closes back to — a mismatch there left a stray straight overshoot at the seam, visible on `star` specifically since its corners alternate rounded/sharp. `polygonCornerRadius`/`cornerTangentPoint` are exported pure functions, unit-tested independently of `Graphics`. `WaypointsRenderer` always draws sharp (`rounded` defaults to `false`, and nothing ever passes it `true`) — corner-style is a teleport-only setting (`teleportCornerStyle`, see above).

### One-way indicator default changed everywhere, not just "Vector by walls"

`WallRenderer.drawOneWayIndicator` (`pixi/renderers/WallRenderer.ts`) draws a bordered, larger triangle by default now — `drawOneWayTriangle(g, cx, cy, dx, dy, { borderColor: canvas.floor.default, borderWidth: 3, size: TILE_SIZE * 0.3 })` — whenever no `OneWayStyleOverride` is passed at all. This is a deliberate shared visual change (GitHub issue #292 follow-up) affecting every caller of `WallRenderer`, not just `VectorByWallsRenderer`: `GenerationRenderer`, `PostEditRenderer`, `PresetConnectionsRenderer` and `MazeOverlayRenderer` all pick up the bordered triangle look automatically, unlike the wall-stroke override above (which is opt-in per caller). `drawOneWayTriangle` itself (`pixi/renderers/wallUtils.ts`) draws via `Graphics.roundPoly` rather than a hand-built `poly` path — `join`/`stroke` alone can't round a filled shape's own corners, only `roundPoly`'s per-corner `corner` radius can — and positions the triangle asymmetrically along its pointing direction: the tip sits 65% of the triangle's length ahead of the wall segment's midpoint, the base 35% behind it (not centered), so the arrowhead reads as protruding from the wall rather than floating over its center. A one-way indicator is always drawn on top of its wall segment (`WallRenderer.render` strokes all wall segments first, then draws every one-way indicator in a second pass) — in every caller, not just `VectorByWallsRenderer`.

`drawOneWayChevron`/`drawOneWayArrow` (also in `wallUtils.ts`) are the two alternative patterns exposed only through `VectorByWallsSettingsPanel`'s "One-ways" section (no other caller ever passes an override, so they never see anything but the default triangle). Both share an `OneWayDrawStyle`'s `thickness` knob for their own line width, independent of `size` (the indicator's geometric scale) — chevron draws two strokes meeting at the tip in a shallow `>` shape (its own `join`/`cap` apply at the vertex and open ends), arrow draws a shaft (ending at the arrowhead's own base, not the tip, so a `square` cap never protrudes past the narrower arrowhead) plus a line-only two-stroke arrowhead. Both support the same outward-only border as the triangle, implemented as a second, wider stroke pass underneath the main one (rather than `alignment: 0`, which only applies to a closed/filled shape's own stroke).

## Scene integration

`MazeScene` wires `ImageExportRenderer` the same way as every other feature-renderer: its own synced layer container, its own entry in `viewportListeners`, `image_export` added to `TESSELLATION_CONFIG_BY_CARD` (resolves to `activeTessellationConfig`, same as generation/post-edit/analytics) and to `refit()`'s `showsMaze` gate.
