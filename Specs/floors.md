# Floors (feature-map card)

GitHub issue #335, part of epic #333. Web-only floor-set configuration UI — add / remove / reorder / title floors. Implemented as the "Floors" card in `FeaturesPanel`, positioned immediately after the tessellation card.

Field shape is per-floor (GitHub issue #338, see `Specs/field-editor.md`). Preset connections are also multi-floor-aware (GitHub issue #340, see `Specs/preset-connections.md`'s "Multi-floor presets") — every preset tool (walls/passages, teleports, markers, locks, split points) can target any floor, though storage stays one flat, maze-wide collection per kind rather than a per-floor bucket; a preset's floor lives in its own `PresetEndpoint.level`. Post-edit is multi-floor-aware too as of GitHub issue #358 (see "Post-edit multi-floor awareness" below) — every post-edit tool can target any floor, with the same flat-collection-plus-`level` storage model. Generation/QC config itself is still maze-wide — every floor shares one rule/stage/strategy setup. Each floor's own field points reach `maze-core` as one entry of `GenerateConfig.level_fields` (GitHub issue #338): generation builds a `level_fields.len()`-level `MultiLevelField<T>` and can connect them with `VerticalPassage`/`Elevator` edges (see `Specs/generation.md`'s "Vertical Connections"). QC/repair/routing during generation is multi-floor-aware; **`compute_analytics` (the WASM entrypoint post-edit's own confirm step drives) is genuinely multi-level as of GitHub issue #359** (own `level_fields`, mirroring `GenerateConfig`'s — see "`compute_analytics` multi-level awareness" below).

## Concepts

**Floor** — `{ id, title }`. `id` is a client-minted UUID (`floor_${crypto.randomUUID()}`), stable across renames/reorders, never reused. `title` is user-editable text, defaulting to `"Floor N"` at creation time.

**Storage order is bottom-to-top** — `floors[0]` is "Floor 1" (the bottom floor), the last array entry is the newest/topmost floor. `addFloor` appends, which is exactly "add on top". The UI renders the reverse of this order (topmost floor first on screen) and maps its visual up/down arrows accordingly — the on-screen "up" arrow moves an entry toward the *end* of the `floors` array, not the start.

**`nextFloorNumber`** — monotonic counter for default `"Floor N"` titles, never reused even after the floor bearing that number is removed. Not derivable from `floors` at load time (a user may rename "Floor 5" and remove "Floor 2..4", after which recomputing from remaining titles would reissue an already-used number) — persisted in the project file.

## Invariant: at least one floor

`floors` always has at least one entry through the UI. `removeFloor` is a no-op when it's the only remaining floor; the UI additionally disables the remove button in that state. A fresh maze starts with exactly one floor, so the card is green (`set`) out of the box — a single-floor maze needs no configuration here at all.

## State fields (mazeStore, `floorsSlice.ts`)

| Field | Description |
|---|---|
| `floors` | `FloorState[]`, bottom-to-top order (see above) |
| `nextFloorNumber` | Next default-title number, monotonic, persisted |

## Actions

**`addFloor()`** — appends a new floor at the end (`floors.length + 1`-th visually, "on top"), title `"Floor {nextFloorNumber}"`, increments `nextFloorNumber`. Its `FloorFieldConfig` (`floorFieldSlice.ts`) starts as a copy of the floor it's stacked on top of — the current topmost floor (`floors[floors.length - 1]`), not the active floor and not the kind's bare default shape (GitHub issue #338, see `Specs/field-editor.md`). Adding, removing, or reordering a floor asks for confirmation when generation/post-edit results exist; confirmation clears those results (GitHub issue #608), but preserves presets.

**`removeFloor(id)`** — no-op if `id` is the only remaining floor or unknown. No confirmation inside the action itself — `FloorsFeature` gates destructive removal behind `ConfirmModal` before calling this, and additionally calls `reset()` first when the removal would discard a generation/post-edit result (see "Loss detection" below). Every preset entry naming the removed floor is dropped (GitHub issue #340: it has nowhere to go), and every preset on a floor above it has its `level` shifted down by one to track that floor's new array position (`dropPresetLevelOnFloorRemove`, `storeHelpers.ts`) — mirrors how this action already deletes the removed id's own `FloorFieldConfig` entry; see `Specs/preset-connections.md`'s "Multi-floor presets".

**`renameFloor(id, title)`** — no-op on an empty/whitespace-only title (trimmed before storing).

**`moveFloor(id, direction)`** — adjacent swap within `floors` in array-index terms (`"up"` = toward index 0 = toward Floor 1, `"down"` = toward the end = toward the newest floor). No-op at either array end or for an unknown id. The UI's own up/down buttons invert this mapping to match the reversed on-screen order — see "Concepts" above. Since `PresetEndpoint.level` is a positional index into `floors` (GitHub issue #340), the swap also remaps every preset's `level` through the same two indices (`remapPresetLevelsOnFloorSwap`, `storeHelpers.ts`) so each preset keeps pointing at the same floor it did before the move — see `Specs/preset-connections.md`'s "Multi-floor presets".

**`copyFloorField(sourceFloorId)`** (`floorFieldSlice.ts`) — replaces the active floor's `FloorFieldConfig` with a copy of `sourceFloorId`'s. Not floors-card UI: exposed as a "Copy floor" button at the bottom of the Field Setup card (`FieldSetupFeature.tsx`, shown only when more than one floor exists), which opens `CopyFloorDialog` — a narrow list of every floor (current floor disabled) plus a Confirm button. Lets a user re-sync a floor's shape to match another floor's at any time, not just at `addFloor` time (see `Specs/field-editor.md`).

## Loss detection and confirmation

Three distinct warnings, per the issue's own contract — removing a floor can lose two independent things, and reordering only ever risks one of them:

- **Field data loss** (`selectFloorRemovalLosesFieldData`, `mazeSelectors.ts`) — `true` when the removed floor's own `FloorFieldConfig.fieldDirty` is set (GitHub issue #338: field shape is per-floor, see `Specs/field-editor.md`). This predicate does not currently account for preset data loss (GitHub issue #340 made presets floor-aware; `removeFloor` silently drops that floor's own presets — see "Actions" above) — extending this warning to cover presets is left to a future issue.
- **Generation/post-edit result loss** (`selectFloorChangeLosesGenerationData`, `mazeSelectors.ts`) — `mazeDirty || postEditDirty`. True whenever a generation result currently exists. Applies to **both** remove and reorder — floor identity shift affects underlying node/graph state, so even a pure reorder (no removal) must warn and reset.

Confirmation message selection (`FloorsFeature.tsx`, on remove):

| Field loss | Generation loss | Message key |
|---|---|---|
| no | no | none — removes immediately |
| yes | no | `floors.confirm_remove_field` |
| no | yes | `floors.confirm_remove_generation` |
| yes | yes | `floors.confirm_remove_both` |

Reorder uses its own `floors.confirm_reorder` message (never the field/preset message) when `selectFloorChangeLosesGenerationData` is true.

**On confirm, when the generation warning was shown, the maze is actually reset** (`useMazeStore.getState().reset()`) before the floor mutation is applied — not merely left stale with a dangling `mazeDirty` flag. A maze left on screen after floor identity changed underneath it would be actively misleading, not just "possibly outdated".

## FeatureCard status

| Condition | Status | Comment |
|---|---|---|
| `floors.length === 0` | `critical` | "No floors configured" — unreachable through the UI (see invariant above); kept per the issue's own status mapping and as a defensive fallback |
| Two or more floors share a title | `warning` | "Two or more floors share the same title" |
| Otherwise | `set` | "Floors configured" |

`computeFloorsCard` (`FeaturesPanel.tsx`) computes this from `floors` alone. The card's subtitle always shows the floor count (`floors.count_active`/`_plural`), independent of status.

## Persistence (project file)

`floors: { floors: { id, title }[], nextFloorNumber }` — optional section on disk (absent in files saved before this feature existed); `validate.ts`'s `validateFloors` defaults to a single floor (`nextFloorNumber: 2`) when the section is missing entirely. A malformed individual floor entry (non-string `id`/`title`) is dropped rather than failing the whole load; an entry sharing an `id` with an earlier one is dropped too (would otherwise collide as a React list key). If every entry is dropped, falls back to the same single-floor default as a missing section. In the post-validation `ProjectFile` type this field is *not* optional — same convention as `dirtyFlags`/`analytics`/`ui` — the optionality is only on the raw JSON on disk.

## Floor switcher (`FloorSwitcher.tsx`, GitHub issue #336)

Shared panel docked top-center over the canvas (`App.tsx`'s `canvasColumn`, absolutely positioned, not full-width) — shows the active floor's title with up/down arrows to move to the adjacent floor. This is the mechanism floor-aware features are expected to use to scope their displayed data to one floor at a time, once such features exist (see "Non-goals" below — none do yet).

Shown for every feature card except `basic_config`, `floors`, and `quality` (`FLOOR_SWITCHER_HIDDEN_CARDS` in `App.tsx`) — tessellation is floor-independent by definition, "Floors" configures the floor set itself, and QC spans the whole maze rather than one floor. Also hidden whenever `floors.length <= 1` — with a single floor there is nothing to switch between.

**State** — `activeFloorId: string` (`FloorsState`, `floorsSlice.ts`), a client-side UI cursor into `floors`. Persisted in the project file as part of `floors` (`ProjectFileFloors.activeFloorId`, GitHub issue #354) — restored on `loadProject`; falls back to `floors[0].id` when the section is missing (files saved before this issue) or names an id that got dropped during floor validation (`validateFloors`, `validatePrimitives.ts`). Also reset to `floors[0].id` whenever `removeFloor` removes the currently active floor. Always a valid id into `floors`; `setActiveFloorId` no-ops for an unknown id.

**Adjacent-floor direction mapping** mirrors `FloorsFeature`'s own inversion: `floors` is stored bottom-to-top, so the switcher's up arrow ("go to the floor above") moves `activeFloorId` toward the *end* of the array, and the down arrow moves it toward the start. Arrows disable at either array end.

**Display label** is `"{n}: {title}"` (`floorDisplayLabel`), a 1-based index prefix (array position + 1) ahead of the floor's own title — e.g. `"1: Floor 1"` — matching the debug panel's own `Lf x:y` bubble-prefix convention (GitHub issue #350, see `Specs/event_log.md`'s "Debug Panel Multi-Floor Awareness" section), both ultimately derived from the same `floors` array position / `NodeDto.level`.

**Panel width** is fixed to the widest floor's own display label (measured via an offscreen `CanvasRenderingContext2D`, `measureMaxTitleWidth` — measures `floorDisplayLabel`'s output, not the raw title, so the index prefix is accounted for too), capped at 300px total — beyond the cap the label truncates with an ellipsis instead of growing the panel further. Computed once per `floors` change (`useMemo`, keyed on the `floors` array), not per active-floor switch, so the panel never reflows/jumps width as the user steps between floors of different name lengths.

Besides the switcher itself, `activeFloorId` now also drives the debug panel's multi-floor awareness (GitHub issue #350: bubble floor prefix/badge, click-to-switch, and auto-switch-on-step — see `Specs/event_log.md`) — see "Non-goals" below for what still doesn't read it.

## Grid visibility while the Floors card is open

`TessellationRenderer` (the sole owner of `GridRenderer` for the tessellation feature — see `maze-web/CLAUDE.md`'s feature-renderer ownership rule) shows its grid while `openCard` is `"basic_config"` **or** `"floors"`. Floors doesn't edit tessellation, so it always draws the confirmed `tessellationConfig`, never `previewTessellationConfig` (that preview-vs-confirmed split is `basic_config`-only, both in `TessellationRenderer` and in `MazeScene.refit`'s own field-config selection passed to `fitFieldViewport`).

## Cross-floor rendering in `GenerationRenderer` (GitHub issue #337 follow-up)

`selectFloorScopedMaze` keeps a `vertical_passage`/`elevator`/`teleport` edge whenever its `from` is on the active floor, even though `to` isn't (`crossesFloorFreely`) — these three kinds are the only ones allowed a dangling cross-floor `to`. Three renderer-level consequences:

- **Vertical-passage/elevator markers** (`VerticalConnectionRenderer`, `buildVerticalConnectionMarkers` in `mazeSelectors.ts`) — one marker per `from` node per edge kind, plus a separate empty/outline marker at a one-way `VerticalPassage`'s arrival-only `to` (found via the unscoped edge list, since a floor-scoped `edges` structurally can't contain an edge whose `from` lives on another floor). Each marker whose `VerticalPassage` resolves a single target floor (`targetFloorIndex`, never set for `Elevator` — its fan can reach several floors at once, so there's no unambiguous click target) is click-to-switch-floor when `interactive` allows it. For an `Elevator` the same `interactive` flag instead makes each of its per-floor number badges (`drawElevatorBadges`, GitHub issue #478 follow-up) its own click-to-switch-floor target — one hit area per badge, wired to that badge's own floor; the elevator marker body itself still never navigates. `interactive` accepts a plain `boolean` (applies to every marker alike — `GenerationRenderer`'s always-on read-only canvas, and the image-export canvas `VectorByWallsRenderer`/`VectorByCorridorsRenderer`, GitHub issue #478, always on too) or a per-marker predicate `(marker) => boolean`, which `PostEditRenderer`/`PresetConnectionsRenderer` (GitHub issue #341 follow-up) use to withhold navigation while the active tool needs the same click for something else: the reset/clear tool (its click means "delete this connection"), and — for a one-way passage marker specifically (`marker.filled === false`) — the one-way vertical-passage tool itself (its click adds a passage there instead, GitHub issue #748). Every marker is drawn at its supplied `pos`; if several markers share a cell, the existing marker draw order is preserved and later markers render on top. An `Elevator`'s own "both" up+down arrow pair still has its internal spread for readability.
- **Cross-floor teleport badges** (`TeleportRenderer`, `buildTeleportEdges`'s optional `floorContext` param in `mazeSelectors.ts`) — when a teleport's `to` resolves (via `resolveNodeLevel`) to a floor other than the active one, the connector's `to` is replaced with the midpoint between `from`'s cell center and the real `to`'s cell center, snapped onto the nearest actual grid coordinate (`nearestCellCoord`, `tessellationGeometry.ts` — an exact world→grid inversion for square/hex/triangle, cube-rounded for hex, parity-disambiguated for triangle; snapping avoids the midpoint landing mid-wall). The symmetric case (this edge's own `from` lives on another floor, `to` is on the active one — e.g. the reverse directed edge of a two-way cross-floor pair, seen from the arrival floor) computes the same kind of snapped midpoint and tags it `fromFloor` instead of `toFloor`; without this branch that pair silently dropped on the arrival floor, since `seenPairKey` already claims the pair from whichever directed edge happened to be listed first. The connector still runs the ordinary routing/collision-avoidance path toward that point; `TeleportEdge.toFloor`/`fromFloor` being set is what tells `TeleportRenderer` to draw a floor-number badge there (a configurable `TeleportFloorBadgeSettings` marker: shape, corner style, size, fill/border colors, border width, gap width, and a label with its own color/weight/size — default a filled circle with a floor-colored digit) instead of an ordinary marker — unless `style.connectorStyle === "none"` (connector display off), in which case the badge follows the connector's own visibility and the point draws nothing at all — not even a fallback ordinary marker, since it's a synthetic midpoint rather than a real teleport node (GitHub issue #519). The midpoint is computed from plain `getCellCenter` values (not `buildNodePositions`'s hub positions, which depend on which floor's own edges are currently feeding `directedPairs`) specifically so the same logical pair resolves to the identical world point whichever floor is asking — required for the badge to sit at the same screen coordinate after switching floors. Badges are click-to-switch-floor whenever `floorNavigable: true` (`GenerationRenderer` and the image-export renderers `VectorByWallsRenderer`/`VectorByCorridorsRenderer` (GitHub issue #478) always on; `PostEditRenderer`/`PresetConnectionsRenderer` on except while the reset/clear tool is active, GitHub issue #341 follow-up). `TeleportEdge.fromFloor` (GitHub issue #357 follow-up, `PresetConnectionsRenderer.ts`'s own `buildPresetTeleportEdges` — see `Specs/preset-connections.md`'s "Cross-floor teleports") is the same badge mechanism for `from` instead of `to`, needed when the on-floor endpoint is the *arrival* end (so it must occupy `to`, pushing the badge onto `from`); `computeFloorBadges` checks both fields, purely by coordinate.

  *Badge collision relocation (GitHub issue #480):* after all cross-floor edges are built, `buildTeleportEdges` runs one `spreadCrossFloorBadges` pass that moves every badge (`fromFloor`/`toFloor` end) off any cell that already carries a center marker or another badge, so no badge is ever drawn stacked on top of something and hidden. **Blocked cells are per-floor.** The exported helper `buildTeleportBadgeBlockedCells(unscopedNodes, unscopedEdges, resolveNodeLevel, startNodeId, finishNodeId)` produces the `TeleportBadgeSpreadOptions.blockedCellsByFloor` map (`Map<floorIndex, [x,y][]>`). Every floor-aware `buildTeleportEdges` caller (`GenerationRenderer`, `AnalyticsRenderer`, `PostEditRenderer`, `VectorByWallsRenderer`, `VectorByCorridorsRenderer`, and the export panels' `useTeleportGroupsAndCollisions`) gets it — together with the matching `TeleportFloorContext` — from one shared assembler `buildTeleportFloorInputs(opts)` (`mazeSelectors/teleport.ts`), which returns `{ floorContext, spread }` from the unscoped node/edge lists, the `floors` array, the active floor id, and the badge-field options; `PostEditRenderer` and `AnalyticsRenderer` pass a distinct `blockedCellsEdges` when the pair-resolution edge list differs from the badge-blocking one (draft edges vs. confirmed `state.edges`). The helper marks, on each node's own floor: split-junction cells (a `${level}:${x},${y}` shared by more than one node), the start and finish node cells (floor from `resolveNodeLevel`), and *both* ends of every `vertical_passage` / `elevator` / `teleport` edge. One-way passage markers are *not* blockers (they sit on cell edges, not centers). **Relocation is floor-independent, and shared with the preset editor.** The relocation core is `resolveCrossFloorBadgeCells(pairs, cfg, blockedCellsByFloor, allowOutOfField, fieldCells)` (`mazeSelectors/teleport.ts`, exported): given the *complete* list of cross-floor pairs (`CrossFloorBadgePair` = a stable `key`, the two `floors` it spans, the grid coords of its two real endpoint cells `endA`/`endB`), it returns a `key → world position` map — deterministic order by `key`, one shared `takenByBadge` accumulator. `spreadCrossFloorBadges` (inside `buildTeleportEdges`) rebuilds `pairs` from `floorContext.unscopedEdges`, keying each by its two node ids sorted, then maps the resolved positions back onto the floor-scoped result edges by the same key (`pairSortKey`, from `TeleportEdge.fromNode`/`toNode`); `buildPresetTeleportEdges` rebuilds `pairs` from the *maze-wide* `state.presetTeleports` and keys them by preset teleport `id`. Either way the badge lands in the identical cell no matter which floor is rendered or which *other* cross-floor badges happen to be visible from it — the active floor never enters the computation, so a pair's two badges (one per floor) stay together across a floor switch. Each pair avoids the **union** of the blocked sets of its own two floors — a 1↔5 teleport ignores floor 2's markers. The desired cell is the snapped pair-midpoint from `getCellCenter` values. **Search:** a displaced badge is placed on the free cell (breadth-first over expanding neighbour rings, `getCellNeighborOffsets`, up to `BADGE_SEARCH_MAX_RINGS` = 10) closest to the straight line joining the pair's two real endpoint cells (perpendicular distance dominant, distance back toward the desired cell as tie-break) — so a badge slides *along* the connector, not off to one side. Cells already taken by an earlier badge this pass are also excluded. If nothing free is found in range, the badge stays on the raw snapped midpoint (pre-#480 fallback). `edge.from`/`edge.to` is rewritten in place; the connector re-routes to follow it. `allowOutOfField` (editor renderers, including presets, pass `true`; image-export renderers pass `!teleportAvoidFieldExit`) and `fieldCells` (all-floor node cells) — with `allowOutOfField: false`, a relocated badge is additionally kept inside `fieldCells`. **Post-edit** passes its *draft* start/finish node ids (resolved from `postEditDraftMeta`), not `state.start`/`.finish`, which still point at the pre-edit endpoints until the draft is confirmed. The preset editor's own per-floor blocked-cell map comes from `buildPresetTeleportBadgeBlockedCells` (`presetConnectionsGeometry.ts`) — the preset analogue of `buildTeleportBadgeBlockedCells`, marking preset start/finish, split-point cells, and vertical-passage/elevator/teleport endpoints — and it (plus the whole `spread` bag) is only built when a preset teleport actually spans two floors.
- **Arrival-only floor for a pure one-way teleport** (GitHub issue #357 follow-up) — a one-way teleport whose `from` lives on another floor is structurally absent from `edges`' own floor-scoping (which only keeps an edge when `from` is on the active floor), so without help the arrival floor would show nothing for it at all, unlike a same-floor one-way teleport's own outline arrival marker. `buildTeleportEdges` additionally scans the *unscoped* edge list for exactly this case (a teleport whose `to` resolves to the active floor and whose `from` doesn't, with no already-produced entry for the same pair) and synthesizes a `TeleportEdge` for it: the real on-floor node is `to`, a `fromFloor`-tagged badge (grid-snapped midpoint, same as the ordinary cross-floor case) stands in for `from`.
- **Wall-fill correctness** (`buildClosedCells`'s optional `allEdges` param) — a one-way `VerticalPassage`/`Elevator`'s arrival-only end lands on a node whose edge is (by floor-scoping) absent from the active floor's own `edges`, so without `allEdges` (the unscoped edge list) that cell is wrongly treated as having no connection at all and rendered as a closed wall. The `allEdges` pass checks both `e.from` and `e.to` against `nodes`, not just `e.to` — needed for `PostEditRenderer` (GitHub issue #359 follow-up), where vertical passage/elevator edges are never part of `activeEdges` at all (neither kind is post-edit-editable), so even a departure-floor cell (whose own `from` is on this floor) would otherwise be wrongly closed, not just an arrival-floor one.

Badge label overflow (label wider/taller than its plate) is reported as the `teleport_badge_text_overflow` / `elevator_badge_text_overflow` export warnings (GitHub issue #707).

The teleport-badge piece is wired in `GenerationRenderer`, `VectorByWallsRenderer` and `VectorByCorridorsRenderer` (image export, both always-on — GitHub issue #478), `PostEditRenderer`, and `PresetConnectionsRenderer` (the latter two gated by tool, GitHub issue #341 follow-up — see the vertical-passage/elevator marker bullet above). The badge is a filled circle with a floor-colored knockout digit by default; in the two image-export renderers its `shape`, `labelType` (Arabic/Roman/letters), `size`, `fillColor`, `borderColor`, label `textColor`, `textFontWeight` and `textSize` (px) are configurable via Export → Teleports → "Floor badges" (`TeleportLineStyle.floorBadge`, GitHub issue #485; fill/border made independently settable in the #503 follow-up, defaulting to the connector colour for the pre-#503 look — see `Specs/image-export.md`'s Teleports section), the border *width* still following the edge marker's own `borderWidth` (not a fixed constant). The label size is the absolute `textSize` (GitHub issue #701) — no per-maze shared fit; `fitTeleportBadgeFontSize` is kept unused for GitHub issue #707. `navigateToFloor` (`renderers/floorNavigation.ts`) is the one shared click-to-switch-floor helper both `TeleportRenderer` and `VerticalConnectionRenderer` call into, rather than each re-deriving `floors[index].id` + `setActiveFloorId` itself. The wall-fill (`allEdges`) piece is wired in `GenerationRenderer`, `VectorByWallsRenderer`, and `PostEditRenderer` (GitHub issue #359 follow-up, passing the unscoped `state.edges`).

`PostEditRenderer` also owns its own `VerticalConnectionRenderer` instance (GitHub issue #358 follow-up, per `maze-web/CLAUDE.md`'s feature-renderer ownership rule — never shared with `GenerationRenderer`'s), drawing `vertical_passage`/`elevator` markers solely from `postEditDraftVerticalPassages`/`postEditDraftElevators` (GitHub issue #341 — see "Post-edit vertical-passage/elevator editing" below). Generation-baked connections are full baseline draft entries (GitHub issue #564), so `state.edges`'s own `vertical_passage`/`elevator` entries are stale mirrors and excluded. It opts into `interactive` as a per-marker predicate (see the marker bullet above), not a plain `true` — clicking switches floor except when the active tool needs that same click for editing.

## Cross-floor badges in the graph overlays (GitHub issue #339, unified under `BaseGraphRenderer` in #367)

`DebugRefHighlightOverlay` also reuses the graph overlays' shared `buildCrossFloorMarkers` and
`drawCrossFloorMarkers` primitives for cross-floor edge, cycle, and issue bubbles (GitHub issue
#449), while retaining its own feature-owned renderer and containers. Its stub uses the same
width, alpha, and endpoint-node marker as an ordinary same-floor debug edge highlight; the shared
badge keeps its floor-number label above its opaque body. A bidirectional edge bubble expands to
both directed pairs so its stub correctly omits the one-way arrow.

`buildNodePositions` (and `buildPathRenderEdges`/`buildPairedRenderEdges` on top of it) is floor-scoped the same way `selectFloorScopedMaze` is — an edge/nav-edge/hop with one endpoint off the active floor silently resolves to only one `Pos`, so the edge itself is dropped. `NavGraphRenderer`, `MazeGraphRenderer`, `PureCyclesOverlay`, `RouteOverlay`, and `IssueHighlightOverlay` each detect this and draw a cross-floor badge at the on-floor endpoint instead of silently losing the connection, mirroring the `VerticalConnectionRenderer`/`TeleportRenderer` pattern above but for graph-overlay edges rather than literal `vertical_passage`/`elevator`/`teleport` edges. All five now extend `BaseGraphRenderer` (GitHub issue #367 — `PureCyclesOverlay`/`RouteOverlay`/`IssueHighlightOverlay` previously hand-rolled their own edge/node drawing).

**`MazeGraphRenderer` cross-floor edge source (GitHub issue #461)** — the base-graph overlay is fed its `edges` from the post-edit draft (`AnalyticsRenderer` builds them via `postEditEdgesToDto`), which by design never carries `vertical_passage`/`elevator` edges (they survive a post-edit confirm on the confirmed `state.edges` graph — see "Post-edit vertical-passage/elevator editing" below). So `MazeGraphRenderer` also takes a separate optional `crossFloorEdges: EdgeDto[]` — the `vertical_passage`/`elevator` subset of the *unscoped* `state.edges` (not `floorScopedStateEdges`, which drops the reverse-direction `EdgeDto` of a bidirectional passage since its `from` is on the other floor — passing both directions is what makes `buildCrossFloorMarkers` emit `direction: "none"` and omit the one-way arrow). These are merged into the pair list handed to `buildCrossFloorMarkers` only — never drawn as ordinary edge lines (`buildPairedRenderEdges`/`buildNodePositions` still see just `edges`). `AnalyticsRenderer` memoises the filter on `state.edges` identity so an unrelated overlay toggle doesn't hand a fresh array to `MazeGraphRenderer`'s identity-based dirty check and force a full graph rebuild. The other four overlays don't need this — they derive their cross-floor pairs from `navEdges`/route hops/issue-loop edges, which already include the vertical hop.

- **`buildCrossFloorMarkers`** (`BaseGraphRenderer.ts`) — shared by all five overlays. Takes the overlay's own edge/nav-edge/hop pairs (already collapsed to `{ from, to }` maze-node-id pairs) plus `nodePos` (the floor-scoped positions) and finds every pair with exactly one endpoint resolved. `resolveNodeLevel`/`resolveNodeCell` (both built from the *unscoped* node list, e.g. `selectNodeLevelResolver`) resolve the missing endpoint's own floor/cell; a missing endpoint that doesn't resolve at all (stale/removed node) is silently skipped, same as the edge itself would be. Emits one `CrossFloorMarker` per distinct target floor in each on-floor cell — nodes sharing a cell are grouped so their badges receive distinct `slot`s (spread evenly around the cell, via `computeCrossFloorBadgePos`'s `slot`/`slotCount`) and their stubs still connect to their respective nodes.
- **`computeCrossFloorBadgePos`** (`renderers/floorBadge.ts`) — resolves the badge's own world position from the on-floor/off-floor cell coordinates, using the on-floor cell's real tessellation vertices (`getCellVertices`, cycling by `slot` — not a fixed 45°, since a tessellation's own corners aren't always at 45°, e.g. flat-top hex). When the badge count exceeds the cell's number of corners, it switches to an even circular distribution and uses `75%` of the normal positioning distance; the badge radius remains unchanged for both positioning clearance and drawing. Same-cell (vertical-passage/elevator style, off-floor node at the identical `(x, y)`) offsets from the on-floor cell center along that angle. Different-cell offsets from the snapped midpoint between the two cells (`nearestCellCoord`, so it never lands mid-wall) along the *opposite* angle, at half the same-cell distance — deliberately off the node→midpoint line so the badge doesn't sit on top of its own stub line.
- **`drawCrossFloorStub`**/**`drawCrossFloorBadge`** (`renderers/floorBadge.ts`) — the connecting line and the badge circle itself (a plain circle with a floor-colored knockout digit, shared with `TeleportRenderer`'s own badge via `drawFloorBadge`). `drawCrossFloorStub` trims the line by `nodeRadius+1`/`badgeRadius+1` at each end (mirroring `drawEdge`'s own margin-trim so the stub doesn't run into either circle's fill) and draws a direction arrow matching the real edge's own `from`→`to` direction (`CrossFloorDirection`: `"toBadge"`/`"fromBadge"` for a one-way pair, `"none"` when both directions exist). The stroke uses a `"butt"` line cap (sharp end, no rounding) for every caller. The direction arrow is centered on the midpoint of the *full* node-center → badge-center span, not the trimmed stroke — the trim is asymmetric (see `nodeGapless` below), which would otherwise pull the arrow visibly off the connection's true center. `nodeGapless` (opt-in, `false` by default; `IssueHighlightOverlay` passes `true`) runs the node end all the way to the node's own center with no `nodeRadius` trim, matching an overlay whose vertex-to-vertex edges are themselves drawn gapless. `NavGraphRenderer`/`MazeGraphRenderer`/`PureCyclesOverlay`/`IssueHighlightOverlay` (all via `BaseGraphRenderer.renderCrossFloorMarkers`) use this arrow-carrying stub. `RouteOverlay` is the one exception — its own route line runs center-to-center with no margin trim and no direction arrows (a route is a single already-directed path, not a set of independently-directional edges), so its cross-floor stub is drawn directly as a plain center-to-center `moveTo`/`lineTo`/`stroke` instead of calling `drawCrossFloorStub`, matching the rest of that overlay's own dots-and-line style; its badge is still drawn via the shared `drawCrossFloorBadge`.
- **Badge/stub color** — `drawCrossFloorMarkers`/`BaseGraphRenderer.renderCrossFloorMarkers` take optional `lineColor`/`badgeColor`/`badgeBorderColor` (all default to the shared `NavGraphRenderer`/`MazeGraphRenderer` cross-floor color). `PureCyclesOverlay` passes its own green for all three; `IssueHighlightOverlay` passes its own red (`HIGHLIGHT_COLOR`) for all three; `RouteOverlay` passes its own yellow (`ROUTE_LINE_COLOR`) directly to `drawCrossFloorBadge` (it doesn't call `renderCrossFloorMarkers`, per the stub exception above) — each badge always matches its own overlay's edge color, never the shared default.
- Every badge is click-to-switch-floor (`navigateToFloor`, the same shared helper `TeleportRenderer`/`VerticalConnectionRenderer` use).
- **`PureCyclesOverlay`'s one-way arrow** — `buildPathRenderEdges`'s optional third param (`reverseCheckEdges`, defaults to its own first param) lets `PureCyclesOverlay` compute `hasReverse` against the *full* nav-edge graph while building path geometry only from the pure-cycle subset — a pure-cycle edge's reverse direction can exist among nav edges without that reverse edge itself being part of the pure-cycle set, and must still suppress the one-way arrow. `hasReverse` requires *both* the reversed endpoint pair *and* the exact reversed node path to be present among `reverseCheckEdges` — this distinguishes a genuine two-way corridor (whose reverse hop retraces the same interior nodes) from a one-way direct hop (e.g. a teleport `[to, from]`) that merely shares its endpoints with a two-way corridor between the same pair; the hop's reversal is absent from the nav-edges, so it keeps its one-way arrow.

## Cross-floor region badges in the Analytics overlays (GitHub issue #345)

`RegionsRenderer` (color-by-`ComponentId`) and `RegionClassesRenderer` (color-by-`RegionClass`) both delegate all cell-fill and badge logic to a shared `RegionOverlayRenderer` (`renderers/RegionOverlayRenderer.ts`, per `maze-web/CLAUDE.md`'s feature-renderer ownership rule — shared logic lives in one base class, never a shared renderer instance); each thin wrapper only picks `componentColors` (`buildPalette` for Regions, `canvas.region[cls]` per `RegionClass` for Region Classes) and forwards to it.

Unlike the graph-overlay cross-floor badges above (one badge per on-floor *node*), a region has no single on-floor node to anchor a badge to — any cell belonging to the SCC region can carry one. A cell gets a region-colored floor badge whenever a `vertical_passage`/`elevator`/`teleport` edge leaves that cell for another floor while staying inside the same SCC region (the region "continues" there):

- **Vertical passage/elevator** (`buildRegionRingMarkers`) — scans the unscoped edge list for `vertical_passage`/`elevator` edges whose `from`/`to` both resolve to the same SCC `components` entry, with the on-floor end on the active floor. Distinct target floors reached from the same cell (e.g. an elevator serving several floors) collapse into one marker with multiple `targets`, sharing one ring of badges rather than each getting a separate ring. Badge position: `computeRegionBadgeRingPos` (`renderers/floorBadge.ts`) — a single badge sits at the cell's own center; two or more spread evenly around a ring centered on the cell, starting straight up (`-90°`) and going clockwise. Ring radius is `(NODE_RADIUS + FLOOR_BADGE_STROKE_WIDTH) * 1.5` — the badge's own outward-drawn stroke (`alignment: 0`) must be included in the radius the factor scales, otherwise adjacent badges' visual (stroke-inclusive) rings overlap despite the bare fill circles sitting that far apart. The factor was raised from `1.25` to `1.5` (GitHub issue #461 follow-up) to spread crowded region cells further apart.
- **Teleport** (`buildRegionTeleportMarkers`) — deliberately *not* handled by the ring geometry above (excluded from `CROSS_FLOOR_KINDS`), since a teleport already has its own dedicated cross-floor badge position (the snapped midpoint computed by `buildTeleportEdges`, see "Cross-floor rendering in `GenerationRenderer`" above). Reuses that *same* `TeleportEdge[]` output — threaded through from `AnalyticsRenderer`, which builds it once per sync and shares it with the maze overlay's own `TeleportRenderer` — so a region's teleport badge lands at the exact same world position as the teleport's own badge, with a connector stub (3px wide, region-colored) drawn from the on-floor cell's center to that shared position, on top of the teleport's own connector.

Badges are always drawn (not hover-only, unlike `RegionHighlightRenderer`'s region highlight) and are click-to-switch-floor (`navigateToFloor`, the same shared helper every other cross-floor badge in this file uses). Each badge is filled in the region's own color with a floor-number knockout digit (`drawFloorBadge`), matching the graph-overlay/teleport badge convention.

**Z-order**: `RegionOverlayRenderer` draws cell fills into one container and badges into a separate one supplied by the caller — `AnalyticsRenderer` wires `regionBadgesContainer`/`regionClassBadgesContainer` above `teleportContainer`/`verticalContainer`/`markersContainer` in its own container tree (added after them), so a region's badge is never occluded by a vertical-passage/elevator/teleport marker drawn at the same cell. The badges container is destroyed and recreated on every `render()` call (mirroring the `resetContainers()` pattern used elsewhere) rather than cleared in place.

`teleportEdges` is computed once per `AnalyticsRenderer.syncAll` only when the maze overlay, Regions overlay, or Region Classes overlay will actually draw with it (`showMaze || showRegions || showRegionClasses`) — not unconditionally, since `buildTeleportEdges` does real routing work.

## Floor badges on `IssuesBlock` bubbles (GitHub issue #365)

Every other cross-floor indicator above lives on the canvas, scoped to whichever floor is active — a floor-scoped highlight can silently hide that the same flagged problem also has entities on other floors. `IssueBubble` (`maze-web/src/components/IssuesBlock.tsx`) adds a plain-React indicator that isn't floor-scoped: a row of solid `L{n}` badges (`IssueFloorBadges`) rendered inside the bubble itself, below its label row, whenever the maze itself has more than one floor (GitHub issue #423) — regardless of how many distinct floors the bubble's own elements happen to touch, matching the Preset Connections orphan-split-node warning's own always-show-on-multi-floor behavior.

- **Touched node ids** — `touchedNodeIds` is the union of every node id this bubble's own visible elements reference, reusing the exact same per-payload-kind sources `handleMouseEnter` already isolates (`loopEdges`/`teleportEdges`/`oneWayEdges`/`splitRouteEdges`/`splitTileNodes`/`visibleRegionGroups` — only this source check's visible elements, not every contributing check's combined, and already filtered by the preset-locked toggle). Covers every preset-lockable payload kind uniformly, no dedicated branch per kind.
- **Floor resolution** — `IssueFloorBadges` resolves each touched node id to a floor index via `selectNodeLevelResolver(nodes)` (same resolver/convention as the canvas cross-floor badges above), memoized on `nodes` identity so it isn't rebuilt per render. A node id that doesn't resolve (stale/removed) is silently skipped, same convention as `buildCrossFloorMarkers`. Distinct floor indices are deduped and sorted ascending, so the row always reads bottom-to-top regardless of `nodeIds`' own order.
- **Rendering** — nothing renders on a single-floor maze (`floors.length <= 1`), regardless of how many distinct floors the bubble's own elements touch. Nothing renders either when `nodeIds` resolves to zero floors (e.g. a whole-maze issue with no per-element highlight data, such as `excessive_scc_count` or an unscoped area-deficit entry) — there is nothing to badge. On a multi-floor maze with at least one resolvable floor, one solid pill-shaped `L{n}` button per distinct floor the bubble's own elements touch (1-based, matching `floorDisplayLabel`'s own index convention) — no localization, fixed `L` prefix. Colors are inverted from the bubble's own severity palette: badge background is `darken(palette.text, 0.2)`, badge text is `palette.bg` — deliberately darker/higher-contrast than the bubble's own text, not reusing it as-is.
- **Click-to-switch-floor** — each badge calls the shared `navigateToFloor` helper (same one every canvas cross-floor badge uses). Badges live inside the bubble's own clickable div (which opens the description modal on click), so the badge's own `onClick` calls `stopPropagation` — a badge click only switches floor, it never also opens the modal.
- **Hover-brightness interaction** — the bubble's own `hoverable-tint` class brightens the whole bubble subtree on hover (`filter: brightness(1.35)`, `global.css`), which would also wash out the badges' own fixed bg/text contrast. The badge row carries a `hoverable-tint-counter` class (only when the bubble is hoverable, i.e. has a `description`) that applies the exact inverse (`filter: brightness(1/1.35)`) when the ancestor is hovered, canceling the brightening back out — filters compose multiplicatively, so the badges stay visually fixed regardless of the parent bubble's hover state.

### Debug event-tree issue bubbles (GitHub issue #467)

The debug event-tree's own inline `issue` bubbles (`DebugRefBubble`, `maze-web/src/components/DebugRefBubble.tsx` — the debug-mode counterpart of Analytics' `IssueBubble`) get the same badge row, for the same reason: a debug-canvas issue highlight is floor-scoped and can silently hide that the flagged loop/region also has entities on another floor. Superseding the single `L{n}` badge sitting *beside* the bubble of GitHub issue #350 (`targetFloorIndex`), `DebugRefBubble` now takes `targetFloorIndices` and renders the shared `FloorBadgeRow` on its own line *inside* the bubble below the label — `bubbleWrap` becomes an `inline-flex` column (`verticalAlign: top`, since the bubble sits inline in the narration text) so the label and the badge row stack, matching Analytics' `IssueBubble` layout. Floor indices come from `resolveIssueBubbleFloors` (`debugTreeSelectors.ts`), computed in `DebugEventTree.tsx` only on a multi-floor maze (`undefined` otherwise): every floor the issue token's structural payload (`{ kind: "cycle"; edges }` or `{ kind: "region"; nodes }`) touches, deduplicated and sorted ascending, unresolved ids skipped — same convention as `IssueFloorBadges`. Only `issue` bubbles get this; every other bubble kind (node/edge/cycle/region) already shows its floor via the label's own `Lf x:y` prefix. Badge colors mirror the `IssuesBlock` convention against the debug issue bubble's own red palette (`ui.debug.issueHighlight`): badge background is `darken(ui.debug.issueHighlight.text, 0.2)`, badge text is `ui.debug.issueHighlight.bg` — the same darker-than-the-bubble-text pairing Analytics' `IssueFloorBadges` uses. `FloorBadgeRow` owns the single-floor hide check and the per-badge `navigateToFloor`/`stopPropagation` click wiring, so a badge click only switches floor, never also opening the reasons modal. (The debug bubble has no `hoverable-tint` brightness filter — that is Analytics-only — so no `hoverable-tint-counter` className is passed.)

## `compute_analytics` multi-level awareness (GitHub issue #359)

`compute_analytics` (post-edit's confirm step and analytics/snapshot recompute) is genuinely
multi-level as of GitHub issue #359 — it no longer collapses every floor onto one `Field`.
`ComputeAnalyticsConfig` (`maze-wasm/src/dto.rs`) gained a `level_fields: Vec<Vec<[i32; 2]>>` field
mirroring `GenerateConfig.level_fields` (one entry per floor, in `floors` order); `build_field_from_nodes`
(`maze-wasm/src/analytics/post_edit.rs`) now builds one `Field` per level, populated only from that
level's own `cfg.nodes` entries (grouped by each node's own `NodeDto.level`). `split_points`/
`preset_split_points` wire triples gained their own `level` entry (`[[x,y], slotId, level]`) — a
`PostEditEndpointDto::Split` gained a `level` field too (`#[serde(default)]`, defaulting to `0`),
disambiguating a slot when two floors share the same `(point, slotId)`. `run_compute_analytics`
drops the previously-hardcoded `all_levels: false` — the snapshot's `NodeDto.level` is accurate
again. The web side (`confirmPostEdit`, `postEditSlice.ts`) sends a `level_fields`-shaped payload
(same derivation `generateConfigBuilder.ts`'s `buildGenerateConfig` already uses) instead of one
flat node/edge list, and parses each `"x,y"`/`"x,y@level"` draft-collection key's own `level` into
the wire triples' `level` slot instead of stripping it.

## Post-edit multi-floor awareness (GitHub issue #358)

Every post-edit tool (wall/passage/reset, split nodes, teleports, start/finish markers) can target any floor, mirroring #340's model for preset connections: `postEditDraftEdges`/`postEditDraftTeleports`/`postEditDraftSplitPoints`/`postEditActiveSplitNode` stay one flat, maze-wide collection each (not a per-floor bucket), with a `PostEditEndpoint`'s floor living in its own `level` field (`{ kind: "split", point, slotId, level? }` — a `node` endpoint carries no `level` of its own, since its resolved `NodeId` already pins it to a real node wherever that node happens to be). The string-keyed collections (`postEditDraftSplitPoints`, `postEditActiveSplitNode`) use the same `"x,y"`/`"x,y@level"` suffix convention `presetSplitPoints`/`lockedNodes` already use (`undefined`/floor 0 has no suffix). Every store action that creates a new split-node `PostEditEndpoint` (`addSplitNode`, `cycleActiveSplitNode`, `resetPostEditPoint`, `applySplitBlueprint`, `resetPostEdit`) stamps `activeFloorLevel(state)` onto it, same pattern preset tools use.

**`resetPostEdit`/`resetPostEditPoint`** no longer restrict to floor 0 — `_generatedNodes`/`_generatedEdges` (already multi-floor since generation is, GitHub issue #337) are grouped per floor first (`groupNodesByLevel`) so a same-(x, y) node on a different floor is never conflated into the same point's split-slot group, then each floor's own rebuilt draft entries are merged into the single flat collection with that floor's `level` stamped on.

**`PostEditRenderer`/`AnalyticsRenderer`/`PostEditController`/`ManageSplitNodesDialog`** all floor-scope before drawing/hit-testing/editing — `selectFloorScopedMaze` narrows `state.nodes`/`state.edges` to `activeFloorId` (same helper `GenerationRenderer` uses), and `recordOnLevel` narrows a plain string-keyed record (`postEditDraftSplitPoints`, `postEditActiveSplitNode`) to the active floor's own entries (stripping the `"@level"` suffix).

For a `PostEditEndpoint` value itself (as opposed to a string-keyed record), the corresponding two-step operation is `floorScopedEndpoint(ep, level, floorNodeIds)` (`pixi/postEditEndpoint.ts`) — checks the endpoint belongs to `level` (`endpointOnLevel`) and, only if so, strips its `level` field (`stripEndpointLevel`), returning `undefined` for an off-floor endpoint. **Always use `floorScopedEndpoint` over calling `endpointOnLevel`/`stripEndpointLevel` separately**: every caller that resolves a maze-wide `PostEditEndpoint` against a floor-scoped, bare-keyed resolver (`buildSplitNodeResolver` built from that floor's own `pointNodeMap`/`splitPoints`) needs both steps together, and skipping the strip step after checking on-level silently reintroduces GitHub issue #425's failure mode — a `split` endpoint's own non-zero `level` makes `resolveSplit` look for a `"x,y@level"` key that isn't in the already-scoped map — with no compiler signal, since `stripEndpointLevel` returns the same `PostEditEndpoint` type as its input either way. `PostEditRenderer.floorScoped`, `AnalyticsRenderer`'s equivalent, `PostEditController`'s teleport-drag and teleport-hit-testing handling, and `ManageSplitNodesDialog`'s `endpointsMatch` all go through this one combinator for exactly this reason (two of these were real, `/code-review`-caught bugs from this pattern being duplicated by hand before the combinator existed).

**`compute_analytics` is genuinely multi-level as of GitHub issue #359** (see "`compute_analytics` multi-level awareness" above) — two floors sharing an (x, y) resolve against their own floor's node, not each other's. `buildSplitNodeResolver`/`resolveEndpoint` (`postEditEndpoint.ts`) accept an optional `level` and fold it into the lookup key when the `nodeMap`/`splitPoints` passed in are themselves multi-floor-keyed, which keeps `resolveEffectiveEndpoints` (image export's start/finish resolution) self-consistent with the now-multi-level WASM call. When `level` is non-`undefined`, the lookup is strictly `"x,y@level"` — no fallback to the bare `"x,y"` key, which would otherwise silently resolve a floor-2 slot against floor 0's own node whenever the two share a coordinate.

**`VerticalPassage`/`Elevator` edges survive a post-edit confirm** (GitHub issue #358 follow-up) — `run_compute_analytics` rebuilding the graph purely from `ComputeAnalyticsConfig.edges` (basic/one_way/teleport) would otherwise silently drop them on the very first confirm. `ComputeAnalyticsConfig` gained `vertical_edges: Vec<VerticalEdgeDto>` (`{ from, to, kind }`, plain resolved `NodeId`s — never a split endpoint, since neither kind is ever wired to a split slot); `restore_vertical_edges` (`maze-wasm/src/analytics/post_edit.rs`) re-adds them into the rebuilt graph verbatim after `build_graph_from_post_edit_edges`, silently skipping any edge whose `from`/`to` no longer exists (e.g. a pruned split node) rather than erroring.

### Post-edit vertical-passage/elevator editing (GitHub issue #341)

Vertical passages and elevators are fully editable in post-edit, mirroring preset connections' own tools 1:1 (same tool set — `vertical_passage_one_way`/`vertical_passage_two_way`/`elevator` — same renderers, same dialogs; only the endpoint addressing differs, `PostEditEndpoint`/node id instead of `PresetEndpoint`/cell+level). `confirmPostEdit`'s `vertical_edges` payload has a single source: `postEditDraftVerticalPassages`/`postEditDraftElevators` (own flat collections, addressed by `PostEditEndpoint`, converted to the wire shape by `postEditVerticalToDto`; an elevator's `floors` list fans out into a full bidirectional mesh, one edge per ordered pair, mirroring `build_preset_state`'s own elevator-establishing loop on the Rust side). Generation-baked vertical passages/elevators are full baseline draft entries with their own stable ids (GitHub issue #564 — see `Specs/post-edit.md`'s Command Log), so editing, removing, or resetting one goes through the same command log as a post-edit-created one; there is no separate generation-time resend or suppression bookkeeping.

**Every click adds a passage (GitHub issue #748).** `startPostEditVerticalPassagePlacement` resolves `availableDirections` (the geometrically possible up/down from `origin`'s field) without looking at passages already drafted there: one available direction → commit it directly (`commitPostEditVerticalPassage`); two → open the direction dialog (`postEditVerticalPassagePending`). A cell may hold several passages to the same floor; opposite one-way passages between the same nodes together read as a two-way connection on confirm. Changing an existing passage's type or direction is the settings tool's job (`setPostEditVerticalPassageDirection`, an `absolute` command — see `Specs/element-tools.md`).

A point reset (`resetPostEditPoint`) prunes the point's commands from the log, so a generation-baked connection returns to its baseline entry (whole elevator mesh included, under its original id) and a post-edit-created one simply disappears.

Persisted in project files as part of `ProjectFilePostEdit.commands` (see `Specs/post-edit.md`).

## Split-node vertical marker anchoring (GitHub issue #555)

Vertical passage and elevator markers use the same directed, non-teleport edge set as graph
rendering when resolving node positions. This preserves shape-aware bridge/diagonal anchors for
split nodes instead of falling back to the generic hub-circle positions.

## Non-goals (deferred to later epic #333 issues)

- No per-floor generation/QC config — every floor shares one rule/stage/strategy setup. Field shape is per-floor as of GitHub issue #338 (see `Specs/field-editor.md`) — kind/orientation stay maze-wide, but each floor's own shape/size/custom points are independent and each reaches core as its own entry of `GenerateConfig.level_fields` (no shared/replicated shape on the wire anymore). Preset connections are floor-aware as of GitHub issue #340 (see `Specs/preset-connections.md`'s "Multi-floor presets") and post-edit is floor-aware as of GitHub issue #358 (see "Post-edit multi-floor awareness" above) — neither is a non-goal anymore.
- Generation now consumes `level_fields` (issues #337/#338) and builds/renders across every floor; QC/repair/routing during generation is multi-floor-aware. `compute_analytics` is genuinely multi-level as of GitHub issue #359 (see "`compute_analytics` multi-level awareness" above). `activeTessellationConfig` remains a single maze-wide snapshot (tessellation *kind* is maze-wide by design, see `Specs/field-editor.md`), but post-edit geometry lookups (hover/hit-testing, split-node topology, "Changes" panel labels) resolve each floor's own `state.floorFields[floor.id].tessellationConfig` instead of this snapshot — a non-active floor's own field shape/size is used even when it differs from the active floor's (GitHub issue #611). `activeFloorId` scopes `GenerationRenderer`'s and `PostEditRenderer`'s displayed nodes/edges, `PostEditController`'s hit-testing, `ManageSplitNodesDialog`'s point resolution, and the debug panel's multi-floor awareness (issue #350).
- No connection between the web `floor.id` (UUID) and core's `LevelId` (`Specs/space.md`) — the web client never sends or receives `LevelId`s, only `level_fields` (one entry per floor, in `floors` order) and, on `NodeDto`, a 0-based floor *index* (`levels_ordered()` position, not `LevelId`). Synchronizing the two identity spaces (e.g. so per-floor preset config could be sent) is deferred to whichever future issue actually needs it.
